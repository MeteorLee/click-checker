# 40. 프런트엔드 배포 종합

## 문서 목적

프런트엔드를 현재 운영 배포 구조에 붙인 결과를 정리한다.  
이번 문서는 준비 문서나 트러블슈팅 문서와 다르게, 최종적으로 어떤 배포 구조와 운영 기준이 자리잡았는지 요약하는 데 목적이 있다.

## 1. 변경 배경

기존 운영 배포는 backend 중심이었다.

- backend Docker 이미지
- ECR
- CodeDeploy
- Blue/Green 전환
- nginx public entrypoint

이 구조만으로도 제품 API는 운영할 수 있었지만, 관리자 콘솔과 제품 API 가이드를 실제 운영 도메인에서 함께 제공하려면 frontend를 운영 배포 구조 안으로 넣을 필요가 있었다.

이번 단계에서의 목표는 다음 두 가지였다.

- 기존 backend Blue/Green 구조를 깨지 않는다.
- frontend를 같은 도메인 아래에서 자연스럽게 제공한다.

즉 frontend를 새로 배포 가능한 상태로 만드는 동시에, 기존 backend 운영 서사를 유지하는 것이 핵심이었다.

## 2. 최종 배포 구조

최종 구조는 다음과 같이 정리된다.

```text
사용자
-> https://clickchecker.dev
-> nginx
   -> /api/**, /actuator/** -> active backend (blue or green)
   -> /, /guide, /login, /signup, /_next/** -> frontend
```

배포 구조는 다음과 같다.

```text
GitHub Actions
-> backend image build / push
-> frontend image build / push
-> 배포 번들 생성
-> S3 업로드
-> CodeDeploy deployment 생성
-> EC2 hook 실행
   -> backend pull + Blue/Green 전환
   -> frontend pull + recreate
   -> nginx config 적용
   -> health / validate 확인
```

즉 현재 기준은 다음과 같다.

- backend: Blue/Green 유지
- frontend: single container
- public entrypoint: nginx same-origin path routing

## 3. 핵심 적용 사항

### 3.1 frontend standalone 이미지 추가

- `frontend/Dockerfile`
- `frontend/.dockerignore`
- `frontend/next.config.ts`

Next.js는 `standalone` 산출물 기준으로 이미지화했다.  
frontend는 별도 Node runtime 컨테이너로 배포되며, 컨테이너 내부 포트는 `3000`, 호스트 loopback 노출 포트는 `127.0.0.1:3001` 기준으로 운영한다.

### 3.2 frontend health check 추가

- `frontend/src/app/healthz/route.ts`
- `docker-compose.prod.yml`

frontend 전용 health endpoint를 `/healthz`로 고정했다.  
이는 backend의 `/actuator/health`와 역할을 구분하기 위한 기준선이다.

### 3.3 nginx same-origin 분기 적용

- `nginx/click-checker.conf`

public nginx는 이제 다음 역할을 맡는다.

- `/api/**` -> active backend
- `/actuator/health`, `/actuator/health/readiness` -> active backend
- `/swagger-ui/**`, `/v3/api-docs/**` -> backend
- `/healthz`, `/_next/**`, `/favicon.ico`, 그 외 페이지 -> frontend

즉 사용자 입장에서는 `clickchecker.dev` 하나만 보지만, 내부적으로는 nginx가 frontend/backend를 나눠준다.

### 3.4 CodeDeploy / ECR 흐름 확장

- `.github/workflows/deploy-prod.yml`
- `scripts/codedeploy/after-install.sh`
- `scripts/codedeploy/application-start.sh`
- `scripts/deploy/deploy-frontend.sh`
- `scripts/deploy/recover-frontend.sh`
- `scripts/deploy/apply-public-nginx-config.sh`

기존에는 `APP_IMAGE` 하나만 다뤘지만, 이번 단계 이후 기준은 다음과 같다.

- `APP_IMAGE`
- `FRONTEND_IMAGE`

backend는 기존처럼 Blue/Green 전환을 유지하고, frontend는 별도 recreate / recover 흐름으로 분리했다.  
즉 frontend 실패가 backend active color 전환 판단을 오염시키지 않도록 책임을 나눴다.

### 3.5 frontend / backend 경로 기준 정리

- `frontend/.env.development`
- `frontend/src/lib/api/config.ts`
- `nginx/click-checker-local-frontend-check.conf`

로컬 개발과 운영 배포가 서로 다른 경로를 혼동하지 않도록 기준을 정리했다.

- local dev
  - frontend: `localhost:3001`
  - backend: `localhost:8080`
- 운영 공개 경로
  - `https://clickchecker.dev`

dev에서는 `.env.development`로 backend `8080`을 직접 보고, 운영에서는 same-origin 상대경로를 사용한다.

## 4. demo 조직 운영 기준

이번 단계에서는 운영 검증용 demo 조직 기준도 함께 정리했다.

- backend `joinDemoOrganization()`은 이제 `organizations.id = 99999`를 기준으로 동작한다.
- local/prod seed 스크립트도 `99999` demo 조직을 재사용한다.

관련 파일:

- `src/main/java/com/clickchecker/organization/service/AdminOrganizationService.java`
- `scripts/data/seed-demo-organization.sh`
- `scripts/data/seed-demo-organization-prod.sh`

즉 demo 조직은 더 이상 이름 중복 상태에 의존하지 않고, 고정 ID를 기준으로 운영 검증에 사용한다.

## 5. 실제 확인 결과

### 5.1 로컬 확인

다음을 확인했다.

- frontend standalone Docker 이미지 빌드 성공
- frontend 컨테이너 `/healthz` 응답 확인
- `docker-compose.prod.yml` frontend 서비스 해석 확인
- local nginx 경로 분기 확인
  - `/healthz`, `/guide`, `/login` -> frontend
  - `/actuator/health`, `/actuator/health/readiness` -> backend

또한 local 조직의 실제 API key로 이벤트 적재를 확인했다.

- `POST http://localhost:8080/api/events`
- 1건 수동 전송 성공
- 추가 30건 랜덤 이벤트 적재 성공

### 5.2 운영 확인

다음을 확인했다.

- `https://clickchecker.dev`
  - 로그인/회원가입/가이드/관리자 콘솔 접근 가능
- 운영 도메인 CORS 허용 후 회원가입 403 해소
- 실제 운영 조직 API key로 `POST /api/events` 적재 성공
- 운영 조직 기준 300건 랜덤 이벤트 적재 성공
- demo 조직 seed와 `데모 조직 추가` 동선 확인

즉 frontend가 운영 도메인 아래에서 실제로 사용 가능하고, backend API 적재/조회와 함께 동작하는 것까지 확인했다.

## 6. 현재 운영 기준

이번 단계 이후 운영 기준은 다음과 같이 정리된다.

- `clickchecker.dev`는 frontend와 backend를 함께 제공하는 단일 공개 도메인이다.
- backend는 기존처럼 Blue/Green 전환을 유지한다.
- frontend는 single container로 운영한다.
- public nginx가 frontend/backend same-origin path routing을 맡는다.
- frontend health는 `/healthz`, backend health는 `/actuator/health`로 구분한다.
- demo 조직은 `id = 99999`를 기준으로 재사용한다.
- frontend 직접 호스트 포트는 내부 loopback 기준이며, 사용자 확인 경로는 항상 `clickchecker.dev`다.

## 7. 결론

이번 단계에서 frontend는 더 이상 로컬 개발 산출물이나 별도 정적 화면이 아니라, 현재 운영 배포 구조 안에서 실제로 배포되고 검증되는 구성요소가 됐다.  
기존 backend Blue/Green 전환 구조는 유지하면서도, 사용자에게는 `clickchecker.dev` 하나로 관리자 콘솔과 제품 API를 함께 제공하는 기준을 만들었다.

즉 이번 작업의 결과는 단순히 frontend를 띄운 것이 아니라, 현재 운영 배포 구조를 `backend-only`에서 `frontend + backend` 서비스 구조로 확장한 것이다.
