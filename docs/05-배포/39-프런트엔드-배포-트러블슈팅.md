# 39. 프런트엔드 배포 트러블슈팅

## 문서 목적

프런트엔드를 운영 배포 구조에 붙이는 과정에서 실제로 발생한 문제와, 무엇이 진짜 배포 문제였고 무엇이 확인 경로 혼선이었는지 정리한다.  
이번 문서는 Next.js frontend, nginx same-origin 분기, CodeDeploy/ECR 연동, demo 조직 검증 과정에서 드러난 문제를 기록하는 데 목적이 있다.

## 1. frontend Docker build가 CI에서만 실패한 문제

### 상황

- 로컬에서는 frontend Docker 이미지가 빌드되는 것처럼 보였는데, GitHub Actions에서는 아래 단계에서 실패했다.

```text
COPY --from=builder /app/public ./public
...
"/app/public": not found
```

### 원인

- `frontend/public` 디렉터리는 비어 있었다.
- 로컬 작업 디렉터리에는 빈 폴더가 존재할 수 있지만, Git은 빈 디렉터리를 추적하지 않는다.
- 따라서 CI checkout 결과에는 `frontend/public` 자체가 없었고, Dockerfile이 이를 무조건 복사하려다 실패했다.

### 대응

- `frontend/Dockerfile`에서 `public` 디렉터리 복사를 제거했다.
- 현재 프로젝트는 `public` 아래 실제 정적 파일을 사용하지 않으므로, standalone 산출물과 `.next/static`만 복사하도록 정리했다.

### 정리

- 이번 문제는 Next.js 빌드 실패가 아니라, 빈 디렉터리를 항상 존재한다고 가정한 Dockerfile 문제였다.
- frontend Dockerfile은 실제로 필요한 산출물만 복사하는 쪽이 더 안전하다.

## 2. 로컬에서 `localhost:3001`로 접속했을 때 회원가입/로그인이 404처럼 보인 문제

### 상황

- `npm run dev` 기준으로는 회원가입/로그인이 되는데,
- Docker나 배포 구조를 확인하는 과정에서는 브라우저 네트워크 탭에 아래와 같은 요청이 보였다.

```text
Request URL: http://localhost:3001/api/v1/admin/auth/signup
Status Code: 404
```

- 처음에는 frontend 배포나 nginx 라우팅이 잘못된 것으로 보였다.

### 원인

- 현재 운영 구조는 다음 전제를 갖는다.
  - 페이지 요청은 frontend가 받는다.
  - `/api/**` 요청은 nginx가 backend로 보낸다.
- 그런데 `localhost:3001`은 nginx를 거치지 않고 frontend 컨테이너 또는 dev 서버에 직접 붙는 경로다.
- 즉 브라우저가 `/api/...`를 보내도 backend가 아니라 frontend 자신에게 요청하게 되고, 그 결과 404가 났다.

### 대응

- 운영 확인 기준 경로를 `https://clickchecker.dev`로 고정했다.
- 로컬도 역할을 분리했다.
  - 개발용: `localhost:3001`
  - backend: `localhost:8080`
  - nginx 경로 분기 확인용: `localhost:18080`
- 또한 frontend API base URL을 env 기준으로 정리했다.
  - dev: `.env.development`에서 `http://localhost:8080`
  - prod: same-origin 상대경로

### 정리

- 이번 문제는 backend API 부재가 아니라, nginx를 거치지 않은 frontend 직통 접속 문제였다.
- frontend 포트와 운영 공개 도메인을 같은 의미로 보면 쉽게 혼선이 생긴다.

## 3. 운영 도메인 `clickchecker.dev`에서 회원가입이 403이 난 문제

### 상황

- 운영 배포 후 `https://clickchecker.dev/signup`에서 회원가입을 시도하면 403이 발생했다.
- 같은 시점 `login`/`signup` 화면 자체는 정상적으로 열렸다.

### 원인

- Spring Security에서 `/api/v1/admin/auth/**` 자체는 `permitAll`이었고, CSRF도 비활성화돼 있었다.
- 하지만 server-side CORS 설정의 허용 origin 목록에 `https://clickchecker.dev`가 빠져 있었다.
- 브라우저 요청에는 `Origin: https://clickchecker.dev`가 포함됐고, Spring의 CORS 필터가 이를 허용하지 않아 403을 반환했다.

### 대응

- `SecurityConfig`의 허용 origin 목록에 아래 값을 추가했다.
  - `https://clickchecker.dev`
  - `http://localhost:18080`
  - `http://127.0.0.1:18080`

### 정리

- 이번 문제는 브라우저 same-origin 개념 자체보다, server-side CORS 허용 목록 누락에 가까웠다.
- 운영 공개 도메인을 실제 허용 origin 목록에 반드시 포함해야 한다.

## 4. same-origin 전환 후 `Failed to construct 'URL': Invalid URL`이 발생한 문제

### 상황

- frontend를 same-origin 기준으로 정리한 뒤 일부 화면에서 아래 런타임 오류가 발생했다.

```text
Failed to construct 'URL': Invalid URL
```

### 원인

- API 경로를 `https://...` 절대경로 대신 `/api/...` 상대경로로 바꿨다.
- 그런데 analytics 쪽 일부 코드는 여전히 `new URL(buildApiUrl(...))` 패턴을 사용하고 있었다.
- `new URL("/api/...")`는 base origin이 없으면 유효하지 않으므로 런타임 오류가 났다.

### 대응

- `frontend/src/lib/api/config.ts`에 `buildApiUrlObject()`를 추가했다.
- 절대경로면 그대로 `new URL(...)`을 사용하고,
- 상대경로면 `window.location.origin` 또는 기본 origin을 붙여 URL 객체를 만들도록 수정했다.

### 정리

- same-origin 전환 시에는 단순 문자열 요청과 URL 객체 생성 로직을 구분해서 봐야 한다.
- 상대경로 자체는 정상일 수 있어도, 이를 URL 객체로 만드는 코드가 남아 있으면 회귀가 발생할 수 있다.

## 5. 규칙 입력 폼에서 타이핑만 해도 페이지가 죽는 문제

### 상황

- `route templates`, `event type mappings` 화면에서 규칙을 추가하려고 입력하면 아래 오류와 함께 페이지가 죽었다.

```text
Cannot read properties of null (reading 'value')
```

### 원인

- `onChange`에서 `event.currentTarget.value`를 바로 읽지 않고,
- `setState((current) => ...)` updater 내부에서 늦게 읽고 있었다.
- React 이벤트 객체는 updater 시점에 이미 정리돼 `currentTarget`이 `null`이 될 수 있다.

### 대응

- `onChange` 핸들러에서 먼저 `const { value } = event.currentTarget`으로 값을 꺼낸 뒤,
- 그 값을 상태 updater에 전달하도록 수정했다.

### 정리

- 이번 문제는 입력값 검증 문제가 아니라 frontend 런타임 이벤트 사용 방식 문제였다.
- 같은 패턴이 반복되기 쉬우므로 form 입력 코드는 일관되게 정리하는 편이 좋다.

## 6. 운영에서 demo 조직 추가가 500으로 실패한 문제

### 상황

- 운영에서 `데모 조직 추가` 버튼을 누르면 500이 발생했다.
- Sentry에는 아래 예외가 기록됐다.

```text
org.hibernate.NonUniqueResultException: Query did not return a unique result: 4 results were returned
```

### 원인

- 운영 DB에는 `demo_web_shop` 이름의 조직이 여러 개 누적돼 있었다.
- 기존 `joinDemoOrganization()`은 이름으로 단건 조회를 가정하고 있었다.
- demo seed를 반복 실행하거나 예전 데이터가 남으면 이름 중복 상태가 발생할 수 있었다.

### 대응

- demo 조직 기준을 이름이 아니라 **고정 ID `99999`**로 바꿨다.
- `joinDemoOrganization()`도 `organizations.id = 99999`를 보도록 수정했다.
- local/prod seed 스크립트도 `99999` 조직을 재사용하는 방향으로 바꿨다.

### 정리

- demo 조직은 일반 사용자 조직과 다르게, 운영 검증용으로 고정 기준이 필요했다.
- 이번 단계에서는 별도 플래그 컬럼 대신 `99999` 고정 ID를 운영 규칙으로 채택했다.

## 7. demo 조직을 `99999`로 맞추는 과정에서 seed 스크립트가 여러 번 깨진 문제

### 상황

- demo 조직을 `99999`로 고정하는 과정에서 local seed 스크립트가 여러 번 실패했다.
- 대표 오류는 다음과 같았다.
  - `api_key_hash` not-null 제약 위반
  - `organization_members` foreign key 위반
  - `api_key_hash` unique 제약 위반
  - SQL syntax error

### 원인

- 처음에는 `organizations.id = 99999` row를 직접 insert하는 방식으로 접근했다.
- 하지만 organization row에는 API key 관련 필수 컬럼과 unique 제약이 있었고,
- owner membership 이동 순서도 foreign key 제약과 충돌했다.
- 즉 단순 id 치환이 아니라, API로 생성된 정상 조직 row를 안전하게 `99999`로 옮기는 흐름이 필요했다.

### 대응

- 현재 스크립트는 다음 흐름으로 정리됐다.
  - API로 정상 organization 생성
  - 원본 조직의 API key 관련 값을 읽어둠
  - `99999` row를 임시 고유 값으로 먼저 생성
  - owner membership을 `99999`로 이동
  - 원본 organization 삭제
  - `99999` row에 원래 API key 값을 복원
- local/prod 스크립트 모두 이 기준을 공유하도록 맞췄다.

### 정리

- 이번 문제는 demo 조직 기준을 고정하는 것 자체보다, organization row의 제약 조건을 얕게 본 데서 생겼다.
- organization identity를 다룰 때는 membership, API key unique 제약, sequence 정리까지 함께 고려해야 한다.

## 8. 운영 이벤트 적재가 401처럼 보였지만 실제로는 잘못된 키를 본 문제

### 상황

- 운영에서 `POST /api/events`를 여러 번 호출했지만 반복적으로 401이 반환됐다.
- backend 로그에는 다음 경고가 남았다.

```text
api key auth failed: reason=kid_not_found_or_inactive
```

### 원인

- 처음에는 적재 API나 운영 인증 로직 자체 문제로 보였다.
- 하지만 확인 결과, 운영에 보낸 키는 로컬 콘솔에서 만든 조직의 키였다.
- 즉 운영 backend가 그 `kid`를 모르는 것이 정상이었다.

### 대응

- 운영 콘솔에서 실제 운영 조직의 API key를 다시 확인했다.
- 새 `ck_live...` 키로 재시도했을 때 `POST /api/events`는 즉시 `200 OK`를 반환했다.
- 이후 같은 운영 키로 300건 랜덤 이벤트 적재까지 성공했다.

### 정리

- 이번 문제는 적재 API 장애가 아니라, 로컬/운영 콘솔을 혼동해 잘못된 키를 사용한 데서 생긴 오판이었다.
- 운영 검증 시에는 항상
  - 접속한 콘솔 환경
  - 생성한 조직 환경
  - 사용하는 API key 환경
를 같이 확인하는 편이 좋다.

## 현재까지 정리된 기준

- frontend 공개 경로 기준은 `https://clickchecker.dev`다.
- frontend 직접 포트와 운영 공개 경로를 같은 의미로 보지 않는다.
- 운영 도메인은 Spring CORS 허용 origin 목록에 포함한다.
- same-origin 전환 후에는 URL 문자열/URL 객체 생성 코드를 따로 본다.
- demo 조직은 `organizations.id = 99999`를 기준으로 재사용한다.
- 운영 적재 검증 시에는 API key가 어느 환경에서 발급된 것인지 먼저 확인한다.
